# 南枫知识库验收构建与空间治理计划

## Objective

消除南枫知识库验收流程按版本重复保存完整 Cargo 编译树的行为；将可再生成的构建缓存和当前验收程序迁至 E 盘的受控目录；保留源码、Git 回溯、必要证据和当前运行程序。完成后，新验收版本不再按版本号增加约 2GB，C 盘不再因该流程持续膨胀。

已确认的根因是当前启动器把版本化目录设为 Cargo 目标目录，见 `scripts/launch-current-acceptance.ps1:6-10`、`scripts/launch-current-acceptance.ps1:31-40`。根目录 BAT 也直接绑定当前 v142 程序，见 `启动南枫知识库-当前验收.bat:4-20`。现有清理脚本仍保留 v93，和当前入口不一致，见 `scripts/cleanup-acceptance-artifacts.ps1:11-30`、`scripts/cleanup-acceptance-artifacts.ps1:72-77`。

## Scope and Guardrails

- 范围仅限 `C:\Users\Administrator\Documents\软件开发\nanfeng-intelligence` 的验收构建、构建缓存、启动器、清理策略和相关交接文档。
- 物理存储目标为 `E:\CodexData\NanfengKnowledgeBase\runtime-qa`；项目中继续保留 `.runtime-qa` 兼容路径，避免历史文档、当前 BAT 和脚本失效。
- 不修改、打开、迁移或删除 `D:\南枫知识库` 的正式数据；不发布、不签名、不推送远端。
- 不把 Git 已跟踪源码、锁文件、文档、截图证据或隔离数据目录当作编译缓存清理。`.runtime-qa` 被 Git 忽略，见 `.gitignore:8-9`，其中可能包含不应直接删除的隔离资料。
- 清理历史副本、删除旧 `src-tauri\target` 或替换目录为联接都属于破坏性操作，必须在清单复核与南烛枫明确确认后执行。

## Verification Criteria

- 新一次验收不会创建带新版本号的完整 Cargo 目标目录；受控运行时目录中只有一个共享构建缓存和一个当前验收应用位置。
- 当前 BAT、启动器 `--verify`、构建标签、EXE 文件大小和 SHA-256 指向同一个当前验收应用。
- 构建进行中或当前 EXE 运行中，脚本拒绝覆盖并提供可定位的原因；不会强制终止进程或删除运行文件。
- `--prepare` 和 `--verify` 不打开、不迁移、不写入 `D:\南枫知识库` 正式数据；真实桌面路径仍只由南烛枫手动执行。
- 清理工具在未收到明确确认时只输出候选清单；该清单明确排除证据、隔离数据、正式发布构建和当前应用。
- 验证后 C 盘项目目录不因版本递增新增约 2GB 的 Cargo `deps`/`build` 副本；共享缓存物理空间位于 E 盘。
- 回溯一个功能时可由 Git 提交、锁文件、构建元信息和轻量证据定位并重建；不依赖旧编译缓存目录。

## Potential Risks and Mitigations

1. **`.runtime-qa` 中存在隔离数据或包含真实内容的报告，不能按目录名批量删除。**
   Mitigation: 先生成按用途分类的清单，采用显式允许列表而非宽泛的 `-app` 或 `-build` 模式；对用途不明的目录默认保留并单独询问。

2. **当前 v142 验收程序正在运行，覆盖或移动它会中断南烛枫的桌面验收。**
   Mitigation: 在迁移和替换前检测可执行文件路径对应的进程；运行时只报告阻塞，待南烛枫关闭窗口后再继续。

3. **目录联接、路径切换或 E 盘短暂不可用可能让旧 BAT/脚本找不到应用。**
   Mitigation: 使用复制、文件数与字节数比对、联接路径读取和 `--verify` 的顺序；原 C 盘目录先重命名保留，直到启动器与 BAT 均验证通过才按授权处理旧副本。

4. **共享缓存被清理后首次 Rust/Tauri 构建会变慢。**
   Mitigation: 默认保留共享缓存；把清理视为独立操作，并提前说明预计会触发一次完整重编译。

5. **历史文档仍引用旧版本目录，删除后会失去可点击的旧路径。**
   Mitigation: 更新当前交接文档只指向固定入口；历史文档保留其证据描述、Git 提交与 SHA-256，并标记旧路径为历史定位信息而非运行依赖。

6. **直接运行未纳入启动器的 Cargo/Tauri 命令仍可能生成 C 盘 `src-tauri\target`。**
   Mitigation: 把共享缓存入口写入项目开发规则与常用脚本，并在实施后用目录审计验证没有新的 C 盘目标目录增长。

## Alternative Approaches

1. **仅定期执行清理脚本：** 改动最少，但根因不变，下一批验收版本仍会持续生成完整缓存，不采用。

2. **保留所有版本化构建目录但整体迁到 E 盘：** 能释放 C 盘，但 E 盘仍会无限增长，且不改善回溯质量，不采用。

3. **只覆盖项目内 `.runtime-qa`，不使用 E 盘：** 能阻止版本级增长，但共享缓存仍占用 C 盘，与系统盘空间目标不一致，仅适用于 E 盘不可用时。

4. **采用一个 E 盘共享缓存、一个固定当前验收应用、轻量证据和显式例外复现区：** 同时保留隔离验证、快速增量构建、功能回溯和可控容量，为本计划推荐方案。

## Execution Gates

- 阶段 A：仅修改脚本、文档与运行时布局；不删除历史文件。停止条件是新的验收不再创建版本化完整构建树，且当前 BAT 与 `--verify` 通过。
- 阶段 B：向南烛枫展示历史候选清单、预计可回收空间和排除项；只有收到明确“确认清理”后才删除候选。
- 阶段 C：如需回收 C 盘的既有 `src-tauri\target`，单独确认并在关闭相关开发进程后处理；它不属于源头修复的前置条件。
