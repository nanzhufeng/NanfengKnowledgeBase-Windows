# 主规格对齐与实施路线

## 结论

当前应用已经具备可靠的本地数据、导入、原件归档、Markdown 阅读、导出、备份和 Windows 桌面基础，但产品信息架构仍以“扁平记录”为中心。主规格要求的核心是“来源进入主题并推动判断演化”，因此不应继续把 Topic、Source Item、Note、Judgment、Evidence 和 Question 塞进现有 `Record`。

当前正确路线是：

1. 用隔离假数据原型验证完整知识演化链路。
2. 冻结对象职责、主路径/关系规则和操作语义。
3. 设计可回滚数据库迁移和兼容读模型。
4. 实施确定性分类器与固定验收数据集。
5. 先在隔离数据副本升级，再考虑正式数据。

## 已确认的现状能力

- Tauri 2 + React/TypeScript + Rust + SQLite/FTS5，本地离线可用。
- 原件先归档、SHA-256、批量队列、有界预览和失败隔离。
- ChatGPT/Claude 会话由软件本地提取可见分支，不依赖模型。
- Markdown/GFM/Obsidian 子集、安全清洗、角色区分、来源附件。
- 搜索、标签、版本、回收站、完整导出、换机备份和恢复。
- 深色单侧栏、冷灰工作台、白色卡片、语义色和统一动效。

这些能力应作为后续 Source Item、Note、Search、Export 和 Backup 的基础设施复用。

## 关键差距

| 主规格要求 | 当前实现 | 风险 | 原型中的解决方向 |
|---|---|---|---|
| 领域 / 主题 / 子主题树 | 扁平标签和记录列表 | 无法表达稳定主路径、别名和关系 | 左侧主题树 + 横向关系区 |
| 来源与笔记分离 | `Record` 同时承担来源、摘要、判断、证据 | 对象职责继续膨胀，迁移困难 | 收录箱 Source Item + 主题知识页 |
| 可解释自动分类 | 导入后直接形成记录/标签 | 用户无法判断为什么归类 | 置信度、五层分数、理由、候选、相似来源 |
| 全量进入收录箱 | 导入中心关注字段映射 | 缺少整理队列和人工确认 | 收录箱为第一入口 |
| 合并/拆分治理 | 无主题级结构操作 | 重复主题会持续积累 | 合并预览/确认/撤销；拆分只预览 |
| 判断演化 | 记录版本，不是主题判断时间线 | 难以看出跨来源变化 | Judgment Snapshot + Turning Point |
| 证据锚点 | 记录内文本列表 | 证据难以定位原始来源 | Evidence 关联来源与时间/段落锚点 |
| 研究上下文 | 单篇导出 | 无法跨时间复用主题结论 | 本地 Context Compiler |

## GitHub 参考的取舍

### 采用

- [TriliumNext/Trilium](https://github.com/TriliumNext/trilium)：借鉴任意深度层级、同一内容的多位置/关系表达、面包屑和版本思路。南枫知识库仍坚持唯一主路径，其他连接作为关系，不复制主题。
- [paperless-ngx](https://github.com/paperless-ngx/paperless-ngx)：借鉴原件保留、消费管线、规则匹配、审计和 dry-run。特别约束分类必须发生在内容提取之后。
- [Karakeep](https://github.com/karakeep-app/karakeep)：借鉴“一切先进入收录箱”、批处理和规则入口。模型自动打标签不进入本地 MVP。
- [SiYuan](https://github.com/siyuan-note/siyuan)：借鉴细粒度引用、双向关系和来源锚点，用于 Evidence 与 Source Item。
- [SilverBullet](https://github.com/silverbulletmd/silverbullet)：借鉴可查询对象和 Markdown 交换层，不引入脚本平台。

### 不采用

- 不复制完整编辑器、插件市场或块数据库。
- 不把图谱作为首页或主要导航。
- 不把 LLM 自动打标、向量数据库或 AI 聊天作为 MVP 前提。
- 不引入云账号、同步、协作或第三方数据库所有权。
- [Reor](https://github.com/reorproject/reor) 只作为未来本地相关内容检索参考；其仓库已归档且依赖嵌入模型，不作为当前架构基础。

## 产品入口重构

| 入口 | 核心任务 | 第一屏信息 | 主要操作 |
|---|---|---|---|
| 收录箱 | 判断新来源归属 | 来源、建议主路径、置信度、理由 | 接受、修改、新建、暂不归类、批量接受高置信 |
| 主题浏览器 | 浏览长期知识结构 | 主题树、当前判断、证据、问题、关系 | 打开来源、查看时间线、生成研究上下文 |
| 整理工作台 | 治理结构质量 | 合并、拆分、相似、操作日志 | 预览、确认、撤销、忽略 |
| 全库搜索 | 跨对象检索 | 主题、来源、笔记、命题和证据混合结果 | 过滤对象、定位来源锚点 |
| 导入与导出 | 数据交换和保护 | 导入队列、原件状态、导出/备份 | 批量导入、映射、导出、备份恢复 |

首页不做 BI 看板；后续若增加首页，只呈现“继续整理、最近演化、即将到期问题”三类可行动信息。

## 分期实施

### P0-A：结构原型（已完成隔离实现）

- 假数据完整演示收录箱、解释、接受/撤销、主题树、主题页、合并/拆分预览、时间线和上下文编译。
- 不连接生产仓库，不迁移数据。
- 产物：`src/prototypes/knowledge-evolution/`。

### P0-B：对象与迁移设计（当前：合同与只读预演已实现）

- 确认 Topic、Source Item、Note、Judgment Snapshot、Evidence、Question、Operation Log 的职责和表约束。
- 设计 legacy Record 到 Source/Note/Topic 的兼容映射。
- 所有迁移先在线备份，支持旧版本只读回退，不直接改正式库。
- 当前已有内存 schema contract 和 legacy Record 只读 dry-run；尚未建立正式 migration、兼容读模型或隔离数据副本迁移。

### P0-C：确定性分类器（领域内核已实现，持久化用例待建）

- 固定五层评分和阈值。
- 建立中文别名、实体、规则和 FTS5/BM25 组合。
- 提供 dry-run、解释、批量确认、操作日志和撤销。

### P0-D：结构治理与上下文

- 合并 preview/commit/undo、别名、重定向和快照。
- 拆分只提供建议和内容归属预览。
- 主题页、判断时间线、证据锚点、问题状态和本地上下文编译。

### P1

- Proposition、Hypothesis、证据过期、字幕时间锚点、笔记拆分/合并。

### P2

- 可选本地嵌入检索、离线模型辅助命名、复杂关系视图；仍不改变 SQLite 唯一数据所有权。

## 停止条件

- 原型术语或入口未得到用户确认：停止数据库设计。
- 对象职责仍有两种显著不同方案：先记录决策，不写迁移。
- 分类固定数据集未达到阈值或解释不可读：停止自动应用，只保留建议。
- 隔离副本迁移不能完整回滚：禁止触碰正式数据。
